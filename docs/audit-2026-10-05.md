# Production readiness audit — 2026-10-05

Branch `claude/gifted-galileo-3hhmty` @ 2e38574. Question: can Indahnya go to
real users now?

## Verdict: not yet

The product works. Every flow I drove in a real browser did what it says:
magic-link sign-in, the wizard, guest upload of JPEG, HEIC and video, the
gallery, RSVP, ucapan, seat search, TV, zip, CSV, QR. Authorisation held on
every host route. XSS payloads rendered as text. Photo EXIF and GPS are
stripped. The Stripe idempotency logic is sound.

It is not ready for three reasons:

1. **Two code defects would hurt real guests on the day.** Videos publish the
   guest's GPS location, and one iPhone-format photo freezes the whole server
   for 3–17 s.
2. **Nothing exists for running it.** There is no deploy config, no backups, no
   monitoring and no startup check of config. Purges are permanent, so a bad
   day cannot be undone.
3. **The legal and selling side doesn't match the product.** The privacy
   notice predates Phase B. There is no SSM number or entity. Co-hosts are
   sold on the pricing table but not built.

None of this is large. Rough effort: 2–3 days for the code blockers, about 2
days for the ops baseline, and owner decisions for the legal items.

## Blockers — fix before the first real majlis

### B1. Public videos carry the guest's GPS location (verified live)
`server/worker/process-media.ts:88`. The ffmpeg transcode copies container
metadata into the served copy.

**Reproduced:** I uploaded an MP4 tagged `location=+03.1390+101.6869/` through
the guest page. The served copy in the *public* bucket still has `location`
and `location-eng`. Android phones write this tag.

This contradicts `/privasi` and the two-bucket design. Photos and posters are
clean (checked: 0 EXIF tags).

**Fix:** add `-map_metadata -1 -map_chapters -1` here, in `utils/audio.ts:46`, and in `kad/assets/[aid].post.ts:183`.

### B2. HEIC decoding freezes the whole server, and a crashing job loops forever (verified live)
`process-media.ts:136-139`, `kad/assets/[aid].post.ts:85-88`, `plugins/worker.ts:24-34`.

heic-convert is synchronous WASM on the web process's main thread. These are
the worst API response times measured while the worker ran (baseline is 14 ms):

| File | Server unresponsive |
|---|---|
| 12 MP HEIC | ~3.5 s each |
| 48 MP HEIC | **16.2 s** |
| 11 JPEGs, including 48 MP | ≤ 18 ms (sharp is threaded; fine) |

Memory peaks at 0.5 GB per 12 MP HEIC and 1–1.75 GB per 48 MP HEIC. Two at
once can OOM a 2–4 GB VPS. `claim()` never checks `attempts`, so a job that
kills the process is re-claimed every 15 min and kills it again. Anyone can
send HEIC: any guest slot, or the public `_cuba` sandbox.

**Fix:**
- Decode HEIC in a child process with a pixel check and a timeout (a sharp/libvips build with libheif, or `heif-dec`).
- Add `and attempts < 3` to the claim query.
- Pass `timeout` to every `execFile(ffmpeg|ffprobe)`.

How often this bites depends on whether iOS Safari hands over HEIC or JPEG
for `accept="image/*"`. Android HEIC arrives as-is. Even 5% HEIC at a
1,000-guest wedding is minutes of a frozen TV and frozen uploads.

### B3. Wedding-day capacity: the worker shares the web process, in one FIFO queue
`plugins/worker.ts:18`.

Two job slots serve everything, and photos queue behind 100 MB videos
(~20–30 s of libx264 at every core each). Estimated peak: 200 guests sending
4,000 photos and 200 videos in an hour needs ~10,000 slot-seconds against a
capacity of 7,200. The TV falls 20–60 min behind, and two x264 jobs starve
SSR. The landing promises "dalam beberapa saat … atas skrin dewan".

**Fix:**
- Run the worker as its own PM2 app (`WORKER=0` on the web app already exists).
- Process photos before video, with a video lane of 1.
- Run `ffmpeg -threads 2` under `nice`.

### B4. No way to run, watch or recover it
- **No deploy artefacts:** no PM2 ecosystem file, nginx config, VPS setup, CI, or migrate/rollback steps. `drizzle-kit` is a devDependency. sharp's native binary means `.output` must be built on Linux.
- **No backups:** no `pg_dump`, no off-box copy, no restore drill. Purge and "Padam majlis" are instant and permanent (`events/[id]/index.delete.ts:12`).
- **No observability:**
  - no health endpoint, uptime check or error tracking
  - `REFUND NEEDED` (`stripe/webhook.post.ts:44`) is a log line nobody reads
  - failed jobs end silently
- **No startup validation of config.** A missing `NUXT_PUBLIC_SITE_URL` silently becomes `http://localhost:3180` in magic links, Stripe return URLs, mails and **printed QR codes**. That cannot be fixed after printing. Missing S3 config points at `127.0.0.1:9000`.

**Fix:**
- Add a Nitro plugin that exits on missing or non-https production config.
- Add an ecosystem file: cluster mode with 1 instance, `kill_timeout` 35 s, `HOST=127.0.0.1`, and logrotate.
- Write an nginx template.
- Run a nightly `pg_dump` to a separate bucket and test one restore.
- Add `/api/health` (DB, worker tick, oldest pending job) with an external uptime check.
- Send Sentry errors and a mail to the owner on REFUND NEEDED and on failed jobs.

### B5. Rate limits are spoofable unless nginx is set exactly right
`utils/rate.ts:17` trusts the **leftmost** `X-Forwarded-For`. nginx's usual
`$proxy_add_x_forwarded_for` appends to the header, so the client's own value
stays first. A random XFF per request then disables every IP limit:

- magic-link mail (free use of our SMTP to mail anyone)
- upload slots
- RSVP
- ucapan
- `/api/cuba`

Nitro also listens on `0.0.0.0`.

**Fix:**
- In nginx, use `proxy_set_header X-Forwarded-For $remote_addr`.
- Behind Cloudflare, use `real_ip_header CF-Connecting-IP` with CF's IP ranges.
- Bind Node to 127.0.0.1.

### B6. Legal and selling copy doesn't match the product
- **The privacy notice (`useLegal.ts`) predates Phase B.** It says guests give no phone number, but RSVP collects one. It doesn't mention:
  - voice recordings
  - meal and RSVP data
  - names and tables visible to anyone with the link
  - bank account numbers and family phone numbers on the kad

  Cross-border transfer is one vague line.
- **No legal identity:** no SSM number, registered name or address, which the e-commerce regulations require. The refund clause is still unreviewed (PLAN.md).
- **Co-hosts are sold but not built.** RM59 says "1 co-host" and RM99 says "5 co-host". Tetapan says "akan datang", and no endpoint adds a member. Either build the invite flow (with a server-side count against `PLANS[plan].cohosts`) or take co-hosts off the pricing.
- **"Paling ramai pilih" / "Most popular"** (`useLanding.ts:99,212`) is claimed before any customer exists. Remove it.
- **"Download semua (zip) … kualiti asal" isn't true for video.** The zip carries the 720p CRF25 transcode, not the original (`download.get.ts:55`). Verified: the zip's mp4 differs from the uploaded file. Zip the originals.

## High — fix before charging money, or in the first week

- **H1. Hide, delete and purge don't reach the CDN.** `utils/storage.ts:85` writes every served copy as `public, max-age=31536000, immutable`, and `move()` keeps that header. Behind Cloudflare, a hidden or purged photo keeps serving from the edge and from browsers. That breaks "link lama terus tak berfungsi" and the deletion promise. **Fix:** a short max-age plus a cache rule, or purge by URL through the CF API on hide/delete/purge.
- **H2. The free 50-upload cap can be locked with zero bytes (verified live).** Pending slots count toward the cap for 3 h 10 min (`utils/events.ts:181`, `worker/purge.ts:38`). Three anonymous requests with two cookies made the gallery answer "Galeri ni dah penuh". This also happens by accident: a guest picks 30 photos on bad 4G and leaves. **Fix:** stop counting pending slots after ~15 min, or cap each guest's share of a free event.
- **H3. Purge doesn't re-check its event.** `purgeEvent` (`worker/purge.ts:8`) deletes with no guard, while renewal is still offered past grace (`utils/plans.ts:71`). Failure: a host pays a renewal between the purge being queued and it running (a retry after an R2 error, or a worker down), and the paid gallery is deleted. **Fix:** lock the row and bail unless the event is still due for purge, and stop offering renewal after grace.
- **H4. A slow ffmpeg run can delete finished media.** ffmpeg/ffprobe have no timeout, and a job locked for more than 15 min is re-claimed while still running. Both runs write the same keys, the loser's `land()` then calls `delEverywhere` (`process-media.ts:186`), and the row says `ready` with no files. **Fix:** a timeout on ffmpeg, heartbeat `locked_at`, and per-attempt keys.
- **H5. The uploader stalls on real phones.** `useUploader.ts`:
  - Batch 2 (photos 31–60) waits until batch 1 finishes *processing*, up to ~6 min (line 76). Closing the tab loses those photos.
  - The XHR has no `timeout`/`onabort`, so a stalled PUT freezes the queue forever.
  - There is no Wake Lock and no `beforeunload` warning.
  - There is no offline queue, despite PLAN's "queued offline (Service Worker)".
  - A retry restarts the whole 100 MB file.
- **H6. Retention mails can fail and photos are deleted anyway.** `worker/notify.ts:93-105` awaits each `sendMail` with no try/catch, so one bad address aborts every warning after it, every hour. Purge never checks that a warning went out. **Fix:** catch each mail separately, and don't purge without a recorded warning, or alert when that happens.
- **H7. Payments are reinterpreted when they land, not when they were priced.** `webhook.post.ts:47` recomputes `kind` and `plan` from the event's current state. Two people paying the same RM40 upgrade turns the second payment into a full renewal. **Fix:** expire the event's other open sessions when one is paid, assert amount and currency, set a short `expires_at` on checkout sessions, and handle `charge.refunded`.
- **H8. A freed slug can be taken over.** Deleting an event or changing its slug releases the slug immediately. Anyone can re-create "Aina & Hakim" and take over the printed QR and the WhatsApp links, *with their own bank account in salam kaut*. **Fix:** keep slug tombstones that are never reusable and redirect to the new slug.
- **H9. Purge and account deletion leave personal data.** The `kad` row (parents' full names, contact phones, bank account numbers) survives purge and deletion. There is no account-deletion path, and `events.owner_id` has no ON DELETE, so a manual delete fails. This conflicts with the "minta dipadam" promise.
- **H10. The zip isn't resumable.** There is no Content-Length or Range, so a 20 GB download that drops restarts from zero. nginx buffering spools to disk. **Fix:** send `X-Accel-Buffering: no`, and offer parts or per-file links.

## Medium

- **Voice ucapan can get stuck.** The row is set to `processing` before `voiceSlot()`, which sits outside the try (`ucapan/[id]/complete.post.ts:31`). On a 503 it stays `processing` for about 3 h. The worst-case request (30 s queue plus 3 × 60 s ffmpeg) exceeds nginx's and Cloudflare's timeouts.
- **No browser-side check of video length.** A 75 s clip uploads in full before it is refused. Reading `<video>` duration first would catch it before upload. 100 MB is already only ~35–45 s of 4K or 1080p.
- **`_cuba` sandbox:** 40 MB photos, HEIC allowed, sharing the wedding queue, and served from the public bucket. It works as free image hosting and as a lever on B2.
- **"Padam majlis" is instant.** Give it a 7-day delayed purge with a restore option.
- **Missing indexes:**
  - `media.guest_id`: scanned under the upload advisory lock, so this one also slows uploads
  - `messages.guest_id`, `rsvps.guest_id`, `reactions.guest_id`
  - `event_members.user_id`, `payments.event_id`, `tables.event_id`
  - `media (event_id, status, id)`: queries sort by `id`
  - a partial index on `jobs`
- **An upload can stick at `uploaded`.** The status update and `enqueue` are separate statements (`uploads/[id]/complete.post.ts:121`), so an enqueue failure leaves the row there forever.
- **kad GC deletes every asset of a live kad** if its saved fields stop validating (`worker/kad-gc.ts:25`).
- **No Content-Security-Policy.** Every page also loads `rsms.me/inter` render-blocking from a third party. Self-host Inter as the other fonts already are.
- **Lightbox images are too big for phones:** the 2400 px JPEG (~1 MB), with no 1200 px size. The TV refetches the full id list every 6 s.
- **Shutdown kills work in flight.** PM2's default 1.6 s `kill_timeout` cuts off zips, transcodes and jobs, and `pg` has no `pool.on('error')`.
- **Tests:** 41 unit tests cover pure helpers only. 0 of 59 API handlers and 0 workers are tested, and no CI runs either gate.

## Low

- **Sign-in tokens:**
  - `/masuk?t=` spends the token on load, with no click: login CSRF, and JS-running mail scanners can burn it.
  - Session and magic tokens are stored in plaintext.
  - Expired sessions, login tokens and done jobs are never pruned.
- **Download filenames:** no RFC 5987 `filename*`, so non-Latin guest names are dropped from zip entries. HEIC originals go in the zip as `.heic`.
- **Slugs:** `mula` is not in `RESERVED` (`utils/slug.ts`). A slug race returns 500 instead of 409.
- **Small crashes and limits:** `?limit=-5` on the guest feed returns 500. `name.post` and `react.post` have no IP limit and create guest rows freely.
- **PLAN.md is stale:** it says a 2-year lead cap, but the code uses 540 days.
- **Hardcoded domain:** the dashboard sidebar shows `indahnya.my/<slug>` regardless of the site URL.
- **npm audit:** 11 high in production deps, all via Nuxt CLI/listhen and build tooling, none on the request path. Revisit on the next Nuxt release.

## What is solid (verified)

- **Authorisation:**
  - A second account got 403 on every host route: event, media, kad, rsvps, tables, ucapan, download, CSV, QR, PATCH and DELETE.
  - Guest routes are scoped by event and cookie.
  - Delete is owner-only.
- **Escaping:** `<script>` in the couple's names and `<img onerror>` in an ucapan render as text in the dashboard, kad, gallery and TV.
- **Privacy of photos:**
  - Served photos carry no EXIF or GPS.
  - Orientation is applied, and HEIC converts.
  - The 60 s video limit is enforced on the server.
  - Originals stay in the private bucket.
- **Sessions:** httpOnly, Secure, SameSite=Lax, 192-bit tokens. The magic link is single-use and expires in 15 min.
- **Stripe:**
  - The webhook is verified against the raw body.
  - The paid transition is a single conditional UPDATE, so it can't apply twice.
  - FPX `unpaid` waits for `async_payment_succeeded`.
  - Prices are MYR and created on the server.
  - Without keys, checkout returns a clean 501.
- **Clocks:** follow PLAN, and an upgrade keeps the paid anchor.
- **Downloads:** CSV has a UTF-8 BOM and a formula guard. Zip, CSV and PNG are sent as attachments with readable names.
- **Layout:** no horizontal overflow on any page at 390 px or 1560 px. Phone inputs are ≥ 16 px, and there are no breadcrumbs.
- **Throughput:** one process serves the kad SSR at ~126 req/s (p50 376 ms at 50 concurrent), the gallery API at ~690 req/s and the TV API at ~800 req/s. That is plenty for one wedding. The landing renders at ~83 req/s with 276 KB of HTML, so have nginx cache it.
- **Repository:** the build is clean. There are no secrets in the tree or the history, and `.env*` is git-ignored.
